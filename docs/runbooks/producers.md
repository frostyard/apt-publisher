# Producers

Runbook for registering, changing and retiring a producer repository. Index:
[docs/README.md](../README.md). The contract it follows:
[specs/producer-interface.md](../specs/producer-interface.md). The operations:
[operations.md](operations.md). How it fits together:
[design/overview.md](../design/overview.md).

## Add a producer

Three steps, in this order.

1. **Register it.** Add a line to `config/producers.tsv` by PR, since `main`
   is protected. `tests/check-config.sh` validates the file: 7 columns, a valid
   `attested` value, codenames the producer may publish to, a component every
   one of those codenames publishes, and `keep` as `-` or 1 to 999.
   - Confirm the package names the producer ships first. Column 2 is a list
     of shell globs, and every `.deb` in a release must match one.
   - Package names in the legacy `stable` suite: `frostyard-*`, `incus*`,
     `bootc`, `libostree-1-1`, `voxtype`, `ttfx`, `tensaku`, `omawrite`,
     `omacut`, `omacalc`, `moonlight-qt`, `kapsule*`,
     `hyprland-preview-share-picker`, `herdr`, `gpu-screen-recorder`,
     `cliamp`, `aether`, `igloo` and `snow-first-setup` (arch `all`). Both
     `frostyard-igloo` and `igloo` exist, from a rename, and `kapsule*` has no
     producer, because `github.com/frostyard/kapsule` does not exist.
2. **Share the token.** Add the repository to the org secret
   `APT_PUBLISH_TOKEN` without disturbing the existing list:

   ```sh
   gh api -X PUT "orgs/frostyard/actions/secrets/APT_PUBLISH_TOKEN/repositories/$(gh api repos/frostyard/<repo> --jq .id)"
   ```

   Avoid `gh secret set --org --repos`: it *replaces* the list.
3. **Change the producer's release workflow.** Replace its "Publish to
   frostyard repo" and "Kickoff snosi" steps with the `publish-deb` dispatch
   step in [specs/producer-interface.md](../specs/producer-interface.md).
   - The token is `APT_PUBLISH_TOKEN`; the producer needs no GPG key and no
     R2 credentials.
   - `R2_*` and `REPOGEN_GPG_KEY` in the org are limited to snosi, so no
     producer has them to remove.
   - frostyard/updex#432 is the template for tag-released Go producers,
     including its contract test and its PR description. frostyard/incus#6 is
     the template for producers that release from branch pushes.
   - The snosi build is dispatched by the publisher, after the packages are
     live, so the producer's own "Kickoff snosi" step goes away.

### Provenance and retention columns

- **`attested`** (column 4) is `no`, or `WORKFLOW@refs/tags/PATTERN`, or
  `WORKFLOW@refs/heads/BRANCH` ([ADR-0004](../adr/0004-pin-the-signer-workflow-of-attested-producers.md)).
  With a policy, `fetch-release.sh` verifies every `.deb` with
  `--signer-workflow` and `--source-ref`, so both the signing workflow and the
  ref are pinned. `yes` is not a value. A producer without build attestations
  stays `no` until it adds `actions/attest-build-provenance`.
- **`keep`** (column 7) is an integer N from 1 to 999, or `-` for no limit
  (core ADR-0067). With N, a publication withdraws every version older than
  the newest N of each of the producer's packages, counted per architecture,
  in the same run. See [operations.md](operations.md#retention-keep-the-newest-n).

## Producer-specific notes

- **incus.** Its release workflow is generated by `sync-docker-build.py`:
  change the generator, not `builds-docker.yml`. Each push to its `stable`
  branch builds Debian 13 amd64 and publishes a GitHub release of exactly five
  `.deb` files, and the build requests `trixie` only.
  - Its versions
    (`1:7.5.1-debian13-202610031200`) carry `-debian13-`, which is not a
    `~debNN` marker, so it is registered for `trixie` only until they carry
    `~deb13` or `~deb14`. A forky build would append `~deb14`, and
    `-debianNN-` already orders a Debian 13 build below a Debian 14 build.
  - Its attestations name `refs/heads/stable`, so its policy names that
    branch.
- **bootc-debian.** It is registered `trixie` only, `~deb13`, and it is a
  public repository, so `fetch-release.sh` and the audit read its releases
  with `github.token`.
  - It releases from manual `workflow_dispatch` runs of `build.yml` on
    `main`, so its policy is `build.yml@refs/heads/main`.
  - Its versions carry `~deb13`. GitHub lists release assets with `.` in
    place of `~`, and aptly keeps those names for the pool files.
  - A forky build needs a `debian:forky` build with `~deb14` versions,
    per-codename `Depends`, and an ostree at least 2026.4, because Debian
    forky ships libostree 2026.4-1.
- **A private producer** needs a token with Contents read for
  `fetch-release.sh` and the audit, or it must go public as bootc-debian did.
- **omarchy-apps** is registered `keep=2`: the publication that adds a newer
  version withdraws the rest of its packages (core ADR-0067).
- **chairlift** is `trixie` only until a smoke test on a forky image passes.
  Its GTK4/libadwaita are loaded at runtime with no `Depends`.

## Change a producer's component

A producer's `component` column is `main` or `image` (core
[ADR-0059](https://github.com/frostyard/core/blob/main/docs/adr/0059-publish-image-only-packages-in-a-separate-apt-component.md)).

1. Change column 6. The codenames the producer lists must publish that
   component.
2. Run **move** with `dry_run` first, then for real: every published version
   whose component differs moves, in one publication per codename. See
   [operations.md](operations.md#move-packages-between-components) and
   [design/overview.md](../design/overview.md#moving-packages-between-components).
   Until the move runs, the producer's publications fail closed on the
   one-component rule.
3. To revert, register the producer for its old component and run the move
   again: a move is reverted by a forward change, never by a rollback.

## Retire a producer

**The rule.** Removing a producer row stops only new publish runs. Two paths
can still bring the name back, and neither may run after the withdrawal:

- a re-run of an old publish run: it checks out its own, older commit, which
  still registers the producer;
- a rollback to a snapshot that lists the name: `switch.sh` does not judge
  names without a producer, so the rollback restores them.

The withdrawal batch and this page must say that neither path may run after
the withdrawal. Unregistration alone never keeps a name out.

So a retirement lands in one PR: it adds the batch file in `withdrawals/`,
removes the producer's row, and records the retirement below with the batch
file's name. Run **withdraw** with the batch (and `dry_run` first) only after
that PR has merged.

### Retired producers

- **first-setup** (`snow-first-setup`), retired 2026-11.
  - The batch `withdrawals/2026-11-05-snow-first-setup.txt` withdraws all 10
    versions in `trixie` main (0.1.1 to 0.4.1, `Architecture: all`), with no
    soak, and only after the PR that adds it has merged. The pool files stay.
    `forky` never had it; the frozen `stable` suite still lists it.
  - **Neither path may run:** do not re-run a publish run of first-setup, and
    do not roll `trixie` back to a snapshot that lists `snow-first-setup`.
  - To bring it back on purpose (for example to revert frostyard/snosi#1224):
    restore the producer row by a PR, then dispatch publish for first-setup
    v0.4.1.
  - Chairlift replaced it on Snow and Snowfield. No published package depends
    on it, and no snosi build input names it. The audit no longer reads its
    releases.
- **gchlog**, retired (repository archived 2026-10-21). It was never
  registered and never published, so no batch exists and no path can restore
  it.

### Not ported

By decision, pilothouse and snowcat-cockpit were not moved to the publisher:
snosi does not install them from APT, and their old repogen deb steps fail
for lack of credentials. snowcat-cockpit is archived.
